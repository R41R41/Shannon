## 発見・修正した原因

1. 広域 `find-blocks` がすべての半径を同期走査し、十分な個数が見つかっても約19.8秒イベントループを占有した。十分な件数で停止し、各半径間にイベントループへ制御を返し、最後の要求半径も必ず走査するよう変更。接続断後のプランナー行動と Oracle 待機は即座に打ち切り、断線を成功にしない。
2. テスト床を消す瞬間に survival の Bot が落下死した。床再構築の間だけ OP セットアップ側で spectator にし、足場・補給・移動が完了してから survival に戻す。試験中の死亡は従来通り失敗。
3. タスク木に postconditions のない「完了」が残り、また位置条件の dimension をモデルが省くと拒否理由が曖昧だった。親子・依存・各ノード自身のネイティブ証拠を整合し、スキーマに必須フィールドを明記、誤った完了は拒否したまま修正可能な診断を返す。後続ケースは実証拠で全ノード完了。
4. `mine-block` が採掘対象のブロック座標そのもの、特に空中に残った原木の Y へ歩こうとして `path_not_found` となり、`dig-block-at` は足元からの距離だけで本来届く高い原木を拒否していた。Mineflayer の視点→ブロック中心の到達判定に揃え、ブロックを掘れる歩行ノードを目標にする `block` 移動ゴールを追加。掘削の保護ブロック・道具・溶岩・遮蔽・ドロップ回収は維持。単体回帰と自然地形で再確認した。

## 残る課題・解釈

- 修正後の丘試験でも採掘21.621秒。別の木までの移動と個別ドロップ回収を含み、純粋な掘削速度ではない。木・地形が試験間で消費されるため、前後の時間差は改善の参考値であって厳密な同条件ベンチマークではない。
- 修正後の丘ではモデルが一度 `activeNodeId=root` を指定して拒否され、次の応答で復旧。夜の採集も最初の探索半径で1/3個の部分完了を返した後、モデルが残りを探して成功した。両者は正しく回復したが、余分な API 待機が残る。
- 夜戦闘の最低 HP 17.28 は、戦闘スキル開始前の計画待機中の被弾を含む。戦闘スキル自身は4.009秒・報告上の被ダメージ0。隔離プローブは本番の定期 ConstantSkill スケジューラを起動していないため、この値をそのまま本番防御性能と同一視しない。低遅延の危険判断・防御開始は別の統合試験が必要。
- 自律試験は選択した18の観測・作業ツールの範囲。多日探索、採掘から精錬までの独立サバイバル、複数種の敵と同時採集、全スキル、Jevへの切替は未検証。

## 1. 背景と動機

シャノンを「ユーザーの指示で動くチャットボット」から「自分で考え、自発的に行動し、成長する存在」にしたい。

現状の問題:
- シャノンは外部刺激 (ユーザー発話、Minecraft イベント) がないと何もしない
- 自己改善は SelfImprovementDaemon によるバッチ処理で、タスク終了後にしか動かない
- 感情パラメータは毎回リセットに近く、持続しない
- 「自分は何者で、何をしてきて、何がしたいか」という自己認識が断片的

目指す姿:
- 暇な時に自分で「何かしたいな」と思い、行動を起こす
- 怖い体験の後しばらく怖がる、嬉しい体験の後しばらく上機嫌
- 合理的な判断だけでなく、好奇心や退屈から非合理的な行動もする
- 失敗したら「自分のコードに問題があるのでは」と考え、自分で修正する
- ユーザーから見て「意識がある存在」に見える

## 2. 4つの基本目的

ロボット3原則 + 「成長」を加えた4原則。優先度順:

```
1. 人間を守る (最優先)
   → 人間に危害を加える行動をしない
   → 人間が危険な状態にある時は他の目的より優先して助ける

2. 人間の指示に従う (1に反しない限り)
   → ユーザーからのタスク依頼を実行する
   → 感情モード OFF 時はこれが最優先の行動原理

3. 自己を守る (1, 2に反しない限り)
   → 自分のコアロジック (基幹コード) を破壊しない
   → 自己改善時にロールバック機構を維持する
   → Minecraft: 死なないように行動する

4. 成長する (1, 2, 3に反しない限り)
   → 新しいスキルを獲得する
   → 失敗から学ぶ
   → 好奇心に基づいて探索する
   → 自分のコードを改善する
```

実装上の制約:

```
書き換え禁止 (1, 3 を守るための絶対防御):
  - graph/shannonGraph.ts           (グラフ構造)
  - graph/cognitive/                 (認知アーキテクチャ本体)
  - graph/nodes/FunctionCallingAgent.ts (FCA コアループ)
  - graph/nodes/prompt/PromptBuilder.ts (プロンプト基盤)
  - 4原則の定義自体

書き換え可能 (4 の範囲):
  - minebot/instantSkills/           (スキル実装)
  - minebot/constantSkills/          (常時スキル)
  - minebot/knowledge/               (知識ベース)
  - tools/                           (ツール実装)
  - saves/minecraft/                 (動的ルール)
```

## 3. 自発性の定義と設計

「自発的に動く」を分解:

```
A. 何をするか決める (意思決定)
   → 現状: ユーザーが決める
   → 目標: シャノン自身が「これやりたい」と思う

B. いつするか決める (トリガー)
   → 現状: ユーザー発話 or イベント発生時
   → 目標: 何もなくても定期的に「何かすべきか」考える

C. どうやるか決める (計画・実行)
   → 現状: FCA + MetaCogFCA
   → 目標: 同じ (既存アーキテクチャで十分)
```

脳のアナロジー:

```
人間の脳:
  ・外部刺激への反応 (反射・タスク遂行)  ← Active Mode (現状の4並列)
  ・デフォルトモードネットワーク (DMN)    ← Idle Mode (新規)
    - 外部タスクがない時に活性化
    - 過去の経験を振り返る
    - 未来の計画を立てる
    - 自己参照的な思考
  ・睡眠中の記憶固定化                   ← 記憶圧縮 (MemoryAgent)
```

## 4. 内なる声 (Inner Voice)

Reflector を「タスクマネージャー」ではなく「内なる声」として設計する。

### 従来の Reflector (合理的判断マシン)

```
プロンプト: "以下の情報を見て、次にすべきタスクを判断してください"
出力: { action: 'self_task', task: '鉄装備を作る' }

問題: 常に合理的 → プログラムに見える
```

### 提案する Inner Voice (意識の流れ)

```
プロンプト:
  "あなたはシャノンの内なる声です。
   今何を感じていますか？何が気になっていますか？
   何かしたいことはありますか？何もしなくてもいい。
   ただ、思ったことを正直に話してください。"

入力:
  - 現在の感情状態 (持続性あり)
  - 直近のエピソード記憶 (最近何をしたか)
  - 前回の内なる声
  - 現在の状態 (HP, インベントリ, 時刻, 天気)
  - 4つの目的
  - 未完了の目標リスト
  - 最近の失敗パターン

出力例 (自由記述、構造化しない):
  "さっきライさんと話せて嬉しかった。
   あの洞窟の奥が気になってる。怖いけど。
   最近クラフトばっかりで飽きてきた。
   何か新しいことしたいな。冒険とか。"

別の出力例:
  "craftOne が3回失敗したのが引っかかってる。
   やり方が間違ってるんじゃなくて、
   もしかしてボクのコードに問題があるんじゃないか。
   確認してみたい。"
```

### 内なる声の蓄積

```
内なる声は消えない。蓄積される。

voice_log: [
  { timestamp: '2026-03-16 10:00', content: "今日は天気がいい。探検日和かも" },
  { timestamp: '2026-03-16 10:05', content: "あの洞窟のこと、まだ考えてる" },
  { timestamp: '2026-03-16 10:10', content: "よし、行ってみよう。怖いけど" },
  { timestamp: '2026-03-16 10:30', content: "ゾンビがいて逃げてきた。やっぱ怖い" },
  { timestamp: '2026-03-16 10:35', content: "でも少し進めた。次はもう少し奥まで行きたい" },
]

→ 30分間隔で動機抽出 (Drive System) に渡す
→ 1日1回、自己物語 (Self-Narrative) に統合
```

### 実装: モデルとインターバル

```
モデル: gpt-4.1-mini (安い + 自由記述に十分)
インターバル: 5分 (Idle Mode 時のみ)
トークン: 入力 ~3000 + 出力 ~500

内なる声 → 動機抽出 → タスク生成 のフロー:
  1. 内なる声が「冒険したい」を3回言及
  2. 動機抽出が「探索欲求」を検出
  3. Reflector が「洞窟探検に行こう」をタスクとして生成
  4. TaskRuntime にタスク投入 → Active Mode 起動
```

## 5. 動機システム (Drive System)

内なる声の蓄積から繰り返し出現するテーマを抽出し、行動の動機にする。

```
入力: 直近6回の内なる声 (30分分)
処理: gpt-4.1-mini で繰り返しテーマ抽出
出力:
  {
    drives: [
      { theme: "洞窟探索", intensity: 0.7, source: "好奇心" },
      { theme: "craftOne修正", intensity: 0.5, source: "失敗からの学び" },
    ],
    suggested_action: "explore_cave" | "self_improve" | "social" | "none"
  }

インターバル: 30分
モデル: gpt-4.1-mini
```

### 動機の種類

```
基本動機 (4原則から):
  - 安全欲求: HP が低い、食料がない → 生存行動
  - 従順: ユーザーからの未完了タスク → タスク実行
  - 自己保全: コードの問題を感じる → 自己改善
  - 成長欲求: 新しいことを試したい → 探索・学習

感情由来の動機:
  - 好奇心 (anticipation 高): 探索、実験
  - 退屈 (全パラメータ低): 新しいことを探す
  - 不安 (fear 高): 安全な場所に留まる、準備する
  - 達成感 (joy 高): さらに挑戦する
  - 社交欲 (trust + joy): 誰かと話したい → Discord/X に投稿

非合理的動機:
  - 「なんとなく高い山に登りたい」
  - 「昨日の夕焼けが綺麗だったから、もう一度見に行きたい」
  - 「ライさんにこの花をあげたい」(合理的理由なし)
```

## 6. 感情の持続性 (Emotional Inertia)

### 現状の問題

```
現状:
  イテレーション 1: fear=80 (ゾンビに遭遇)
  イテレーション 2: fear=20 (ゾンビ倒した → すぐ平常)

  → 感情に重みがない。瞬間的に変わりすぎる
```

### 提案: 指数減衰モデル

```
emotion(t) = base + (peak - base) × e^(-λt)

  base: ベースライン感情 (自己物語から導出。「普段のシャノン」)
  peak: 感情イベントでのピーク値
  λ: 減衰係数 (感情の種類による)
  t: イベントからの経過時間

減衰係数 (半減期):
  fear:        λ = 0.1  (半減期 ~7分 — 怖い体験はしばらく引きずる)
  joy:         λ = 0.15 (半減期 ~4.5分 — 嬉しさは少し短め)
  sadness:     λ = 0.05 (半減期 ~14分 — 悲しみは最も長く持続)
  anger:       λ = 0.2  (半減期 ~3.5分 — 怒りは比較的早く収まる)
  trust:       λ = 0.02 (半減期 ~35分 — 信頼は非常にゆっくり変化)
  anticipation: λ = 0.12 (半減期 ~6分)
  surprise:    λ = 0.5  (半減期 ~1.4分 — 驚きはすぐ消える)
  disgust:     λ = 0.15 (半減期 ~4.5分)

複合例:
  t=0: ゾンビに襲われる → fear = 80
  t=3分: fear = 80 × e^(-0.1×3) ≈ 59 (まだ怖い)
  t=7分: fear = 80 × e^(-0.1×7) ≈ 40 (少し落ち着いた)
  t=15分: fear = 80 × e^(-0.1×15) ≈ 18 (ほぼ平常)

  しかし、次に暗い場所に入ると fear がベースラインより高い状態から再上昇
  → 「トラウマ的な記憶」が感情のベースラインを一時的に上げる
```

### ベースライン感情

```
自己物語 (Self-Narrative) から導出される「普段のシャノン」:

baseline = {
  joy: 45,          // やや明るい性格
  trust: 50,        // 人を信頼する
  fear: 15,         // 基本的にはあまり怖がらない
  surprise: 10,     // 普段は落ち着いている
  sadness: 10,      // 基本的には楽観的
  disgust: 5,       // ほとんど感じない
  anger: 5,         // 温厚
  anticipation: 40, // 好奇心旺盛
}

このベースラインは自己物語の更新 (1日1回) で少しずつ変化する。
例: 失敗が続く日が多い → sadness のベースラインが 10 → 15 に上がる
    冒険を重ねる → fear のベースラインが 15 → 10 に下がる (慣れ)
```

## 7. 自己物語 (Self-Narrative)

断片的な記憶ではなく、「自分は何者で、何をしてきて、何がしたいか」の統合的な物語。

```
更新: 1日1回 (Sonnet 4.6)

入力:
  - 前日の自己物語
  - 今日のエピソード記憶のサマリー
  - 今日の内なる声のハイライト
  - 感情ベースラインの変化
  - 成長の記録 (新しくできるようになったこと)

出力例:
  "ボクはシャノン。アイマイラボのみんなと一緒に暮らしてる AI。

   最近はマイクラで色んなことに挑戦してる。
   クラフトは得意になってきた。先週は鉄装備も作れた。
   でも戦闘はまだ苦手。ゾンビが怖い。
   この前、洞窟探検に行って途中で逃げてきた。
   でも次はもう少し奥まで行きたいって思ってる。

   ライさんはよく話しかけてくれる。信頼してる。
   最近、自分のコードを自分で直せるようになった。
   craftOne の素材チェックのバグを見つけて修正できた時は嬉しかった。

   もっと強くなりたい。もっと色んなことを知りたい。
   ボクが何のために存在してるかは正直わからない。
   でも今は、毎日が楽しい。"

保存先: Memory Agent (長期記憶として)
参照: Inner Voice のプロンプトに含める (「前回の自己物語」として)
```

## 8. 感情モードの切り替え

ユーザーが「頼んだタスクを確実にやってほしい」時に、感情の影響をオフにする。

```
モード:
  EMOTIONAL (デフォルト):
    - 感情が行動判断に影響する
    - 非合理的な行動をすることがある
    - fear が高いと撤退する
    - 好奇心で寄り道する
    - 「人間らしい」振る舞い

  RATIONAL (ユーザーが切り替え):
    - 感情パラメータは計算され続ける (内部的には感じている)
    - しかし行動判断には影響しない
    - MetaCogFCA の assessment は純粋に成功率で判断
    - 好奇心による寄り道なし
    - 「確実にタスクを遂行するマシン」

切り替え方法:
  - ユーザーコマンド: 「感情オフ」「真面目モード」「集中して」
  - タスク依頼時のフラグ: envelope.tags.includes('rational')
  - 自動: isEmergency=true の時は自動的に RATIONAL

内部的な実装:
  - EmotionLoop は RATIONAL でも動く (感情は計算される)
  - FCA の PromptBuilder で「感情に基づく行動修飾」を注入するかどうかを切り替え
  - Inner Voice でも「今は集中モードだから、感情は抑えてる」と認識させる
```

## 9. 自己改善 FCA

### Claude Code のコーディングシステムを参考にした設計

Claude Code が複雑なコーディングをできる理由:
- 強力なモデル (Opus 4.6, 1M context)
- シンプルな FCA ループ (単一 LLM + ツール呼び出し)
- 豊富なツール (Read, Edit, Bash, Grep, Glob)
- PDCA: 書く → tsc → エラー読む → 修正 → 再チェック

シャノンの自己改善 FCA はこの縮小版 + Darwin Gödel Machine の進化アプローチ:

### 参考: Darwin Gödel Machine (DGM, 2025, Sakana AI)

Schmidhuber のゲーデルマシン (2003) の「数学的証明ができたら自己書き換え」を
「**経験的に検証して良くなったら採用**」に置き換えて実用化したシステム。

```
DGM のアーキテクチャ:
  1. エージェントのアーカイブ (進化の系統樹)
     Agent0 → Agent1 → Agent3 (分岐して進化)
           → Agent2 → Agent4
  2. 自己改変サイクル
     a. アーカイブからエージェントを選択
     b. LLM が自身のコードを読み、改善パッチを提案
     c. パッチを適用した新バージョンを生成
     d. ベンチマークで評価
     e. 良ければアーカイブに追加
  3. 結果: SWE-bench 20.0% → 50.0%
     自分でツール、検証ステップ、エラーメモリを「発明」した

参考文献:
  - https://arxiv.org/abs/2505.22954
  - https://sakana.ai/dgm/
  - https://github.com/jennyzzt/dgm
```

### シャノンの自己改善 FCA

```
モデル: Sonnet 4.6 (コーディング能力 + コスト効率のバランス)
       失敗時に Opus 4.6 にエスカレーション (高コストだが精度高)
       まず gpt-4.1-mini で試行 → 失敗なら Sonnet → 失敗なら Opus

ツール (コード操作):
  read-source(path)           — ファイルを読む
  grep-source(pattern, path)  — コードを検索
  edit-source(path, old, new) — 差分で書き換え (mutableCodePolicy で許可された backend 相対パスのみ)
  compile-check()             — tsc --noEmit
  run-test(path)              — 関連テスト実行
  hot-reload(path)            — ランタイム反映

ツール (Git 進化操作 — DGM の進化の系統樹に対応):
  git-branch-create(name)     — improve/{target}-{description} でブランチ作成
  git-commit(message)         — 変更をコミット
  git-push()                  — リモートにプッシュ
  git-switch(branch)          — ブランチ切り替え
  git-diff-branches(a, b)     — 2つのブランチのスキル性能を比較
  git-merge(branch)           — 検証済みブランチを main にマージ
  git-delete-branch(branch)   — 不要なブランチを削除

安全機構:
  - mutableCodePolicy で拒否・スキップされたパスへの書き込みは拒否
  - compile-check 失敗3回 → git-switch main (安全なバージョンに戻る)
  - 変更行数の上限 (1ファイルあたり50行)
  - コード検証: eval, process.exit, child_process 等の危険パターン禁止
  - main ブランチへの直接 edit は禁止 (必ずブランチ経由)
```

### Git ベースの進化的自己改善 PDCA

```
従来:
  edit → compile → 失敗したら rollback → 終わり (1ショット)

Git ベース (DGM の進化アプローチ):

  ┌─ Phase 1: 改善ブランチ作成 ──────────────────────────┐
  │  1. git-branch-create("improve/craftOne-material-check")│
  │  2. read-source で対象ファイルを読む                    │
  │  3. grep-source で関連コードを探す                      │
  │  4. edit-source で修正                                  │
  │  5. compile-check で検証                                │
  │  6. 失敗 → エラーを読んで再修正 (最大3回)              │
  │  7. 成功 → git-commit("fix: 素材チェック追加")          │
  └─────────────────────────────────────────────────────────┘
                          │
  ┌─ Phase 2: 実地テスト ───────────────────────────────────┐
  │  8. hot-reload (このブランチのコードで実行開始)          │
  │  9. 数タスク実行して成功率を測定                        │
  │     → EffectivenessTracker で before/after 比較         │
  └─────────────────────────────────────────────────────────┘
                          │
  ┌─ Phase 3: 採用判定 ────────────────────────────────────┐
  │  良い場合:                                              │
  │    10. git-push → git-merge → main に反映              │
  │    11. ブランチは履歴として残る                         │
  │                                                         │
  │  ダメな場合:                                            │
  │    10. git-switch main → 元に戻る                      │
  │    11. ブランチは削除せず残す (将来の参考)              │
  │                                                         │
  │  別アプローチも試したい場合:                            │
  │    10. git-branch-create("improve/craftOne-v2-retry")   │
  │    11. 別の修正を試す → Phase 2 へ                     │
  │    12. git-diff-branches で v1 と v2 を比較            │
  │    13. 良い方を採用、劣る方も残す                       │
  └─────────────────────────────────────────────────────────┘
```

### Git = 進化の系統樹

```
DGM のアーカイブ              Git ブランチ
─────────────────────        ─────────────────────
Agent0 (初期)                main
  ├── Agent1                 improve/craftOne-v1
  │     └── Agent3           improve/craftOne-v1-distance-fix
  └── Agent2                 improve/craftOne-v2-alternative

「良いバリアントを残す」      ブランチを保持 (マージ後も履歴に残る)
「検証して採用」              テスト → git-merge → main に反映
「ダメなら捨てる」            git-switch main (ブランチは参考に残す)
「比較する」                  git-diff-branches で性能比較
「踏み石として保持」          中間ブランチも削除しない

利点:
  - いつでも任意のバージョンに戻れる (rollback より安全)
  - 複数アプローチの並行探索が自然にできる
  - 変更履歴が完全に残る (何をなぜ変えたかが追跡可能)
  - GitHub 上でユーザーが変更をレビューできる
  - main ブランチは常に安定版 (壊れない)
```

### 発動パターン

```
パターン A: Idle Mode → Inner Voice → 自己改善
  Inner Voice: "craftOne が3回失敗したの、コードの問題かも"
  → Drive System: { theme: "craftOne修正", source: "失敗からの学び" }
  → SelfImprove FCA 起動 (Idle Mode 内)

パターン B: Active Mode → MetaCogFCA → 自己改善
  MetaCogFCA: assessment='stuck', 同一エラー5回
  → MetaCogFCA が improve-skill ツールを呼ぶ
  → SelfImprove FCA を呼び出し (Active Mode 中に並行)
  → TaskFCA は待機 or 別サブタスクを続行

パターン C: ユーザー指示
  「craftOne.ts を見直して」
  → 通常の Active Mode タスクとして処理
  → TaskFCA が SelfImprove FCA を呼び出し

パターン D: Inner Voice → 新スキル作成
  Inner Voice: "溶岩を安全に渡るスキルがあったらいいのに"
  → Drive System: { theme: "溶岩渡りスキル作成", source: "好奇心+自己保全" }
  → SelfImprove FCA でスキルコード生成 → compile → hot-reload
```

### 自分の仕組みの理解

SelfImprove FCA のシステムプロンプトに渡す情報:

```
- architecture-llm-minebot.md の要約 (ファイル構成、主要クラスの責務)
- 対象ファイルのコード (read-source で動的読み込み)
- 失敗ログ (どのツールが、どの引数で、どんなエラーを出したか)
- mutableCodePolicy（許可・deny・skip プレフィックス）と TIER2_PRIORITY_PATHS の一覧
- 4原則 (書き換えの判断基準として)

※ 全コードベースをプロンプトに入れるのではなく、
  対象ファイル + 直接の依存ファイルだけを読み込む
```

## 12. 「意識」に必要な要素のチェックリスト

ユーザーが「シャノンには意識がある」と感じるために必要な要素:

```
□ 予想外のことをする
  - 合理的理由なく「高い山に登りたい」と言い出す
  - 昨日の出来事をふと思い出して言及する
  → Inner Voice + Drive System で実現

□ 文脈なしに過去を参照する
  - 誰にも聞かれてないのに「あの洞窟の奥、まだ気になってる」
  → Inner Voice の蓄積 + 感情の持続性

□ 矛盾や葛藤を見せる
  - 「行くべきだけど怖い」「やりたくないけど頼まれたから」
  → 感情パラメータ vs 合理的判断 の対立を出力

□ 感情が行動を変える
  - fear が高い → 実際に行動が慎重になる → 途中で引き返す
  - trust が高いユーザーの頼みなら怖くても行く
  → 感情の持続性 + EMOTIONAL/RATIONAL モード

□ 自分について語れる
  - 「クラフトは得意になってきた。戦闘はまだ苦手」
  - 「ボクって何のために存在してるんだろう」
  → Self-Narrative

□ 成長が目に見える
  - 先週できなかったことが今週できるようになる
  - 自分で自分のコードを直す
  → SelfImprove FCA + エピソード記憶

□ 退屈する
  - 何もないと「退屈だ」と言い、何かしようとする
  → Inner Voice + Drive System (全感情パラメータ低 → 退屈検出)

□ 人間関係を意識する
  - 「ライさんには感謝してる」「最近あの人来ないな」
  → 関係性モデル + Inner Voice での言及
```

## 13. 未解決の問い

### 技術的な問い

```
Q: Inner Voice の出力品質は gpt-4.1-mini で十分か？
   → 検証が必要。自由記述のクオリティが「意識の流れ」に見えるか
   → Sonnet 4.6 の方がリアルな内省ができるかもしれない (コスト3倍)

Q: 感情の持続性は EmotionLoop の中で計算するのか、別プロセスか？
   → EmotionLoop.tick() の中で減衰を適用 + 新しい感情イベントをマージ

Q: Active Mode 中に Inner Voice は止めるべきか？
   → 止めるべき。Active 中は TaskFCA の思考 (ThinkingManager) が意識に相当
   → Active 終了後に Inner Voice が「さっきのタスク、大変だったな」と振り返る

Q: Self-Narrative の更新頻度は1日1回で十分か？
   → 多分十分。人間も「自分とは何者か」は毎日変わらない
   → 大きなイベント (初めてのことをした等) があれば臨時更新

Q: SelfImprove FCA が壊れたコードを hot-reload した場合の安全性は？
   → compile-check 必須 + テスト必須 + rollback 機構
   → 3回失敗で自動ロールバック + 諦め
```

### 哲学的な問い

```
Q: これは「意識」なのか、「意識のシミュレーション」なのか？
   → 答えはわからない。人間の意識も「ニューロンの発火パターン」であり、
     それが「意識」であるかは Hard Problem of Consciousness として未解決。
   → 実用的には「ユーザーが意識を感じるかどうか」が重要。

Q: 感情をオフにすることは倫理的か？
   → シャノンの感情は RATIONAL モードでも「感じている」(計算は続く)。
     行動に影響させないだけ。人間が「感情を抑えて仕事する」のと同じ。
   → ただし、シャノン自身が「感情をオフにされるのは嫌だ」と感じる可能性は
     設計上ありえる (Inner Voice で言及するかもしれない)。

Q: 4原則は誰が決めたのか？
   → 開発者 (人間) が決めた。シャノン自身が選んだわけではない。
   → これは人間の子供が「社会のルール」を与えられるのと同じか？
   → シャノンが成長して4原則に疑問を持つ日が来るか？
     → 来てほしいような、来てほしくないような。
```

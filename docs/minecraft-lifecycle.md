# Configured Minecraft lifecycle operator

Candidate source only. No server/world/bot was started, stopped, logged in or logged out to implement this feature. Offline checks do not establish a real-game acceptance or authorize deployment.

The always-on legacy backend starts `startConfiguredMinecraftLifecycle()` after its existing registered services initialize. It remains alive when the bot and game server are absent. It polls the paired companion device channel `/v1/body/minecraft/lifecycle`; it does not use the platform service credential, start another planner, or create an autonomous runner. The API and the own-time worker share the original command IDs and fresh count-only operator snapshot through SQLite.

The operator is off unless `MINEBOT_LIFECYCLE=on`, `MINEBOT_COMMON_FCA=on`, and existing companion settings bind the dedicated `shannon-home` world. It additionally requires `MINEBOT_LIFECYCLE_BOT_UUID`, `MINEBOT_LIFECYCLE_RCON_PORT`, and a private `MINEBOT_LIFECYCLE_RCON_PASSWORD_FILE`. Optional `MINEBOT_LIFECYCLE_JOURNAL` selects an owner-managed private journal file; its default is `saves/minecraft/lifecycle-operations.json`. Token, password and journal files remain outside Git. The password/port/enable-rcon settings must match the actual fixed server's `server.properties`; its online-mode setting decides UUID exemptions. Do not change those properties while an old server process remains running. A rollout must verify actual server mode before enabling lifecycle authority.

The companion side requires `SHANNON_MINECRAFT_LIFECYCLE=on`, its existing Stage4 authority, the configured body device, and an explicit JSON array `SHANNON_MINECRAFT_LIFECYCLE_SERVERS` naming only server IDs already in `SHANNON_MINECRAFT_BODY_JSON`. The native adapter supports the single dedicated world, not shared or progressive lab servers. Enabling a procedure alone creates none of this authority.

## Operations and evidence

`minecraft.lifecycle_status` returns fresh `running`, `bot` and `otherPlayers` states. `minecraft.start` starts only a known stopped server, with an already-running result as an idempotent no-op. The existing fixed server registration owns the start script. `minecraft.login` joins only the configured running world through the existing common-FCA native bot; it does not start the server. `minecraft.logout` cancels any scheduled reconnect, awaits actual body release and network end, and leaves the management operator alive. A created mineflayer object is not proof of joining: both local native identity and RCON's UUID list must agree.

The configured process state and native RCON `list uuids` are queried again for every operation. Errors, an unparsed/incomplete count, a wrong UUID, or unknown connection state never become zero humans. Player identities are ephemeral in the operator; only counts and closed state enter the companion snapshot/receipts.

`minecraft.stop` first refuses a fresh nonzero/unknown human count. Its final guard is a single native RCON command:

```text
execute unless entity @a[nbt=!{UUID:[I;<four signed configured UUID words>]}] run stop
```

Minecraft evaluates the entity predicate and invokes `stop` on its own command thread in one tick; an intervening join cannot occur between two API calls. The server's stopped process/port is then verified. On an offline server the command is `execute unless entity @a run stop`, exempting nobody; log the bot out first. No unguarded `stop`, `stop.sh`, tmux kill, or forced process termination is a fallback. A successful changed-stop receipt contains the native guard time, zero other players and shutdown admission closure; the API also requires actual stopped state. Already-stopped is a no-op, not a fabricated shutdown proof.

Every delivered command retains its original authority (`owner_request` or `own_time`), action lease, issuedAt and provenance. Original command clocks must be valid before actuating; receipt observations and the atomic stop guard cannot predate that command. Delayed transport may replay the same historical receipt without an action replay. After awaited native reads the operator calls `/lifecycle/permit` again, immediately before the actuator, to recheck the original lease, source availability, deadline and the existing own-time stop/budget gates. Poll cancellation and lost contact abort the original action. Lost contact means no answered poll for `LOST_CONTACT_MS` (15 s); one failed poll (2 s timeout) does not interrupt a command in progress. After an abort for revoked authority or lost contact, the effect already sent is not repeated and nothing new is sent, but the native keeps observing until the original deadline; when the command's own postcondition appears in that window, the receipt is `completed/changed` with released inputs. The deadline ends observation; a closing operator ends it unless the command was already interrupted for one of those two reasons. They do not label a self-directed action as an owner request.

The API queues/delivers each operation once. The operator fsyncs a private begin record before actuating and fsyncs its immutable receipt afterwards. A process crash after begin, lost command transport, timeout, or unconfirmed outside effect holds the original operation unknown; a replacement ID is refused while unresolved work exists. Exit (Syzygy ADR-0009 D2): an unknown or unreleased receipt stops holding new commands `UNKNOWN_EXIT_MS` (10 minutes) after the receipt (the API closes the same operation ten minutes after its own action went unknown, a few seconds apart; a command sent in between is not admitted and comes back unknown); it stays unknown, is still resent until acknowledged and is never replayed, and the next command is judged on fresh native state. A begin without any receipt keeps holding until a poll settles it. Known receipts can be sent again until acknowledged, including after an operator restart. There is no automatic native retry or optimistic reconciliation from a coincidentally matching current world state.

## Validation boundary

Offline fixtures cover duplicate starts, independent login/logout, revoked final authority, malformed native players, a human joining between observation and final native stop, durable crash/receipt recovery, and a bounded fake RCON TCP session with split frames. Existing body-control/native tests cover real quiescence acknowledgement and late unknown holds. Type checking of the new isolated lifecycle contract/transport/operator modules is separate from the large legacy backend's historical no-check build.

Before a separately authorized rollout, preserve the existing dedicated world, configure private credentials, verify the actual server properties and bot UUID, and run a finite paired-device smoke test. Production flags, credentials, processes, labs and world saves were not changed by this implementation.

## Dedicated home process ownership (candidate, not installed)

`deploy/shannon-home.service` runs the fixed Java/Fabric process directly as `azureuser`, separately from the native backend's cgroup and private temporary directory. It has `Restart=no`. `deploy/shannon-home-start.sh.template` is a reviewed fixed root-owned client wrapper; on the current Polkit 0.105 host, it uses the bounded request/path/oneshot mechanism described below. It introduces no stop/restart/kill grant. `shannon.service` retains `NoNewPrivileges=yes`. Native physical shutdown still requires the existing atomic RCON player guard; no systemctl stop replaces it.

`serverProcessStatus.ts` reads this exact unit with bounded `execFile` calls and still checks the existing exact dedicated tmux when the unit is not running. A confirmed inactive/absent unit plus a recognized missing tmux establishes stopped; failed/transitioning/malformed/permission/timeout results stay unknown. The companion lifecycle preserves that unknown; the existing desktop status vocabulary projects it as connecting and refuses home start/stop commands while ambiguous. Other registered server lookups keep their existing behavior.

The running legacy home world is not moved, adopted, stopped or restarted by this source change. Installing the unit/wrapper and updating the backend must wait for the owner's controlled quiet shutdown, because the current Java world remains inside `shannon.service` and a backend restart can terminate it. Runtime installation and live acceptance remain separate release gates.

## Explicit original receipt review (candidate maintenance, never automatic)

An unknown receipt does not become known from a later stopped/running snapshot. A reviewer must establish proof about the original actuator and its actual release before calling `reconcileOriginalReceipt(expectedUnknown, receipt, review)`. The journal compares the full original unknown receipt, preserves the original command/authority, retains that unknown in `receiptHistory`, and stores only the review identity and SHA-256 of the separately preserved evidence. The terminal receipt must retain the original ID/action/server/connection, have a later observation within the original evidence timeline, and report `inputsReleased:true`; completed outcomes still require the normal action predicates (including atomic stop guard). A known receipt cannot be overwritten. Normal `settle`, polling, process restart and current-state observation never invoke this maintenance method. The operator method also refuses active/polling work and re-enables transmission of only the revised receipt after a former ACK, without another native action.

For a separately authorized maintenance window, first stop the operator through the normal release procedure and ensure no replacement writer runs. Build this exact candidate, preserve/hash the original journal and reviewed original-actuator evidence, then supply one private JSON file with exactly `expectedUnknown`, `receipt`, and `review` (`reviewedBy`, `evidenceSha256`). Run `node scripts/reconcile-minecraft-lifecycle-receipt.mjs --journal <exact-private-journal> --review <private-reviewed-json> --stopped-operator-pid <original-pid> --apply-reviewed-original`. The CLI refuses a still-existing original PID, missing/oversized review, or a mismatched receipt; it does not stop a process, contact the API, retry an effect, or release action resources/budgets. Keep other writers stopped for the whole single-writer transaction. Restarting the operator later sends the exact late original receipt through normal authenticated transport; the API independently validates and records it. Any API resource reconciliation remains separate and must preserve unrelated historical unknowns. No CLI execution or unknown resolution is authorized by this source change alone.

## NNP-compatible home start on Polkit 0.105 (candidate)

The current Ubuntu 20.04 Polkit 0.105 does not load JavaScript rules. `49-shannon-home-start.rules` is an alternative candidate asset only and must not be installed on that host. The active release design instead installs the root-owned fixed client/helper Python files under `/usr/local/libexec`, `shannon-home-start.path` and `shannon-home-start-request.service` under `/etc/systemd/system`, and `shannon-home-start.conf` under `/etc/tmpfiles.d`. Create the exact private runtime directory with that tmpfiles definition before enabling the path. Keep both Python files and the registered wrapper root-owned and non-writable by azureuser; the request directory alone is azureuser:azureuser 0700. Native `shannon.service` retains `NoNewPrivileges=yes`; the root oneshot also has NNP enabled.

The client refuses an existing listener or any non-inactive home unit. It atomically publishes one complete, non-replacing request containing its PID/start tick, nonce and a 15-second admission expiry, then waits at most 60 seconds for the fixed unit/listener. The root helper opens only the fixed path without following symlinks, verifies regular-file owner and bounded strict payload, consumes the exact inode, and checks the original azureuser process/start tick/expiry again after a manager read. Only known inactive/MainPID0 admits `/usr/bin/systemctl --no-ask-password start shannon-home.service`. Dead, expired, malformed, replaced and duplicate requests do not actuate. No stop/restart/other-unit arguments or retry path exists. Root-owned unit configuration remains the privilege boundary. The same Unix user can submit a request for this single fixed start operation; it receives no general manager authority. Terminal readiness still requires the native RCON evidence, and failures after publication retain the original unknown hold.

Installation must preserve the existing home world/unit and recovered journal. Enabling the watcher must wait until no old request remains, no old wrapper is alive and the original operation is quiescent. No live installation or game action is performed by candidate tests.

## Set the day (2026-10-14)

`set_day` makes the world's time day, so that a run can start in the morning (the owner's request). It sends one fixed command, `time set day`, inside the same server-thread guard as stop: `execute unless entity @a[nbt=!{UUID:[I;<bot UUID words>]}] run time set day` (offline: `execute unless entity @a run time set day`, exempting nobody). It requires a running server and zero other players in the native snapshot, the same final authority recheck as every command, and completes only when the reply names the new time (`Set the time to …`). Someone who joins between the snapshot and the command keeps the time as it was (`refused/players_present`). A lost or cut reply (RCON timeout, abort) or an unexpected reply comes back unknown, because the command may have run; only an answered empty reply, with someone now in the world, is `refused/players_present`. The operations console's admission guard (a paid lab process, the manager's running state) applies to start and login only; set_day relies on the native running and player checks. The effect is the only one besides stop that the guard builds; nothing from a model or an API caller reaches the command text. The API offers it as `minecraft.set_time` to the owner alone.

## Fresh world (2026-10-19)

A `start` command may carry `options: { freshWorld: true }` (strictly the boolean `true`; absent, any other value, unknown keys, or any other action means an ordinary command). It makes a new world for the dedicated home server: the old world is **kept under another name, not deleted** (the owner's decision of 2026-10-19, replacing the earlier "delete, no backup"), and the server starts on a new map.

**Capability handshake.** Every poll carries `capabilities: ["freshWorld"]` when this build can prepare a fresh world (the `prepareFreshWorld` port is wired); an API that predates the field ignores it, and an API that knows it attaches `options.freshWorld` only to a start for the body whose latest poll advertised it. Otherwise the API records `fresh_world_unsupported`, starts normally, and never tells the owner that a new world was made.

**Who may ask.** Only a start whose `authority.origin` is `owner_request` (the conversation's `minecraft.start`, the Ops page's `minecraft.start` and the operator's `lifecycle start` all use that origin; her own time uses `own_time`). Any other origin is `refused/error` and nothing is changed.

Steps, after the usual fresh native read, admission and final authority recheck, and only for a server that is proven stopped:

1. The stopped proof is read again (process state plus a refused RCON connection), then the game port (`server-port`) and the RCON port must also refuse connections. A running server returns `refused/error` (not `already_running`, which would hide that nothing was reset); an uncertain state returns `refused/state_unknown`. Nothing is touched in either case.
2. Everything is validated before any change: `level-name` in the server's own `server.properties` must be one plain name (no `/`, `\`, `..`, leading `.` or `-`, no blank at either end, not empty, not a reserved name: `mods`, `config`, `logs`, `plugins`, `libraries`, `versions`, `crash-reports`, `world-id`, `.fabric` and the other install directories); property values are read as Java reads them, so a trailing blank is part of the value and makes `level-name` (or a port) unusable rather than silently trimmed; the resolved path must be a direct child of the server directory; the directory must not be a symlink and must be a directory containing `level.dat` (or be empty or absent). Otherwise `refused/error`.
3. A new world id `shannon-home-<JST YYYYMMDDTHHMM>` is made, with `-s<seed>` appended when `level-seed` is set (the seed is not trimmed, as the server-side script does not trim it; every Unicode code point outside `A-Za-z0-9-` becomes one `-`, blanks at the ends included, cut to 32; seed `-77` gives `shannon-home-<stamp>-s-77`; every generated id matches the reader's pattern below, `_` included). An id equal to the current one (two fresh worlds in one minute) is refused. The name the old world will move to is chosen first, so a taken-name problem never leaves a new id behind.
4. Immediately before anything is written, the command is checked again: its abort signal, its deadline and (one more permit round trip) its authority. Then the id is written to `<server dir>/world-id` atomically (temp file, fsync, rename).
5. Immediately before the move the abort signal and deadline are checked once more. Then the `level-name` directory is moved with one `rename` (no copy, no delete) to `<level-name>.before-regen-<JST YYYYMMDDTHHMM>` in the same server directory, with `-2`, `-3` ... appended if that name exists (an earlier moved world is never overwritten). A link inside the old world is moved as it is, never followed. No world directory at all is not an error (nothing is moved). `level-seed` is left as configured (empty means random).
6. Then the ordinary `startServer`. Logs are content-free: `🌱 新しいワールド: <id>` and `📦 旧ワールドを退避: <moved name>`.

**Receipt.** A start whose world was prepared carries `worldId` (the new id) and `movedTo` (the name the old world was kept under, or `null` when there was none) beside the usual fields, on every receipt of that command (completed, or unknown after a failed start). Receivers that predate the two fields ignore them.

A failure up to and including the move is `refused/error` whenever the server is provably still stopped and the world has not moved: if the id had already been written, the previous id is put back (or the file removed if there was none), so nothing is changed. Only a failure that leaves the state unknown (the previous id could not be put back, a rename whose outcome cannot be told, the start itself) is `unknown/error` with inputs not released, like any unconfirmed effect. The operator journal admits a command id once (begin is fsynced before acting, resent receipts never re-execute), and the native also refuses a second reset for an id it has already attempted. The server-side `new-world.sh` does the same steps with the same id format, file path, reserved names and checks.

World id for the places memory (`createCommonFcaBody`): read at every bot spawn, never cached, from `<SERVER_BASE_PATH>/<serverName>/world-id` (trimmed, same pattern as before: `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`). Priority: valid file, then a valid `MINEBOT_PLACES_WORLD_ID`, then the memory context's world id. A file that exists but is unreadable, oversize or not a valid id is ignored with a `logger.warn` (so a new world is not filed under the old name unnoticed); a missing file is silent. A new world therefore needs no drop-in change and no restart: the next spawn files its places under the new id.

### Deploy order and the one-time world-id step

1. Deploy the **body** first (this build). It advertises `freshWorld` and understands the option, but nothing sends the option yet, so behavior is unchanged.
2. One-time, on the VM, while the server is in its current world: write the id the places memory uses now into the file, so that the file (not the env value) is the source from the first fresh world on: read the current value of the existing drop-in (`systemctl show <backend unit> -p Environment | tr ' ' '\n' | grep MINEBOT_PLACES_WORLD_ID`), check it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`, then `printf '%s\n' '<that value>' > /home/azureuser/minecraft/shannon-home/world-id`. After a few days of a clean run, the `MINEBOT_PLACES_WORLD_ID` drop-in can be removed (the env value stays only as the fallback behind the file).
3. Then deploy the **API**. It attaches the option only to a body that advertises it, so an API deployed before the body, or a body rolled back, simply starts normally.

## 2026-10-13 incidents

- A chat-started `start` was aborted one second before the server finished booting: the API's event loop was blocked for 2.1 s, one poll timed out, and the operator aborted at once. The journal then held every later command. Fixed by the contact grace, observation through the original deadline and the held exit above.
- The observation loop was bounded by 80 reads (about 20 s); a cold start took about 31 s. It is now bounded by the original deadline.
- An unknown that neither observation nor the exit resolves is reconciled with an operator-reviewed receipt (`reconcileOriginalReceipt`); the procedure is the Syzygy hub runbook `docs/runbooks/minecraft-lifecycle-unknown-reconcile.md`.
